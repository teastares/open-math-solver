# 求解器基线与扩展性实验计划

日期：2026-10-11。状态：待执行。对应方案见[通用求解器架构与研发路线](../decisions/2026-10-11-通用求解器架构与研发路线.md)，实际资源以[项目概况](../project.md)为准。

本计划用于决定先自研哪些模块、GPU 和集群在哪些模型上值得投入，以及何时继续扩大规模。所有数字门槛均为建议的实验验收标准，不是当前性能结果。尚未连接用户集群、安装求解器或运行求解基准。

## 首轮要回答的问题

1. 在相同原模型精度下，哪些 LP 的瓶颈能被 GPU 有效改善？
2. 真实 MILP 的时间花在根节点、热启动 LP、传播、割还是搜索策略上？
3. 相关 LP 批处理是否能改善整个 MILP，而不仅是 LP 调用吞吐？
4. 增加 GPU 或节点时，端到端收益在何处饱和，原因是什么？
5. 在已有组件之上，自主模块是否带来可归因收益并保持正确性？

## 环境与输入记录

执行前生成固定的实验清单，记录实例哈希、变体来源、求解器精确版本/提交、构建选项、依赖、参数、随机种子及验证器版本。不要把会持续更新的网页 current/latest 当成运行版本。

环境清单至少包括 CPU 型号、物理核数、线程绑定、NUMA、内存、GPU 型号与显存、FP64 能力、驱动、单节点卡数、卡间互联、跨节点延迟/带宽、存储和调度器。记录分配而非全机标称资源，避免共享集群后台负载混淆结果。冷启动和热启动分列。

数据入口：[MIPLIB 基准集](https://miplib.zib.de/tag_benchmark.html)、[MIPLIB 数据与检查器](https://miplib.zib.de/download.html)、[Netlib LP](https://www.netlib.org/lp/)。MIPLIB 的解与状态文件会更新，需要与实例一起保存版本和哈希。该公开集不能替代独立真实模型保留集。

初轮可选 48 个诊断案例：16 个不同规模/结构的 LP、16 个 MILP、8 个相关 LP 序列和 8 个数值边界案例。选择规则在测新算法之前冻结；此小集合用于调试，不用于宣布通用领先。没有真实业务集时，可以完成公开基准研究，但不能作行业效果承诺。

## 对照与公平条件

LP 对照至少包含 CPU 对偶单纯形、成熟内点法、GPU 一阶方法；MILP 对照包含 Gurobi、SCIP 和 HiGHS 的可用固定版本。cuOpt 的适用算法也纳入异构系统对照。使用 Gurobi 所需访问和许可在运行前确认，不在本次设计中假设已具备。

比较分成三张独立成绩表：

- 同硬件、同线程/内存和时间预算的算法比较。
- CPU/GPU/集群不同组合的最低延迟比较，完整披露资源。
- 相同成本或计算预算下的效果比较，披露计价与能耗测量方法。

默认参数与调参结果分列；各方调参预算一致，调参集与保留集分离。现有产品已支持的 GPU、分布式和合适算法模式应纳入相应系统比较，不能只挑弱配置当基线。

所有端到端时间从规定的输入边界计到完成恢复和验证，包含解析、预处理、矩阵转换、主机设备传输、分区、求解、crossover 和 postsolve。模型已常驻的重复求解是另一项独立测试，不与冷启动结果混合。

## 正确性与终止标准

LP 初步设置两档研究精度：一般档绝对/相对容差约为 1e-6，严格档约为 1e-8。它们是测试起点，不是所有应用的默认承诺。外部验证器对原模型分别计算约束、变量界、对偶条件和目标 gap；归一尺度与绝对误差都写入结果。不同求解器的内部同名参数不一定语义相同，需要用外部指标对齐。

MILP 候选解先按整数容差检查；若执行舍入或连续变量修复，必须重新验证全部原模型约束并重算目标。示例研究整数容差为 1e-6。所有性能结论以外部质量通过为前提，不能用更松的容差换取优势。

以最小化问题为例，有有限已验可行目标 U 和有效下界 L 时，统一报告：

\[
g_{\mathrm{abs}}=U-L,\qquad
g_{\mathrm{rel}}=\frac{U-L}{\max(1,|U|,|L|)}.
\]

对照求解器保留自身 gap 日志，同时换算上述共同指标。主要 MILP 性能终点建议为相同的相对 gap 1e-4；另报告 1e-2、1e-3 和更严格终点。业务绝对 gap 阈值另行指定。目标平移和缩放会影响相对指标，因此同一基准保持相同原始目标与常数，绝对 gap 始终同时展示。

通过回调或带时间戳的可行目标/有效界轨迹确定共同指标的首次达标时间。无法精确采集时记录采样误差，并设置足够严格的内部终止条件，避免后端提前停止；不能仅在最终结果换算 gap 就把总时间当作同一终点耗时。外部验算发生在运行后时，另行计入验证成本，并检查被用作达标证据的候选解与界。

缺少可行解或有限下界时，gap 标为未定义/无穷，不填零。若 U 小于 L 且超出明确数值容差，判为错误并调查，不能用截断为零掩盖。对不可行/无界实例单独检查证据和状态，不套用普通 gap 指标。

对节点安全界验证，使用可人工证明的小实例、已知精确解、区间/高精度校验及两套独立实现。重点覆盖 Aᵀy 的舍入误差、无限界、局部割、变换恢复和极端尺度。差分结果一致是证据之一，不代替证明。

每份结果标注 `verification_level`，避免将声明容差的证书通过称作严格数学认证。可用小型有理数实例和 [SoPlex](https://soplex.zib.de/) 的精确 LP 结果交叉检查下界；人为扰动对偶向量，确认无法认证时拒绝给出错误有限界。有限测试通过仍需结合保守计算方法本身的正确性论证。

## 测量与汇总

每次运行保存状态、验证结果、总时间、分阶段时间、峰值 CPU/GPU 内存、首个可行解时间、各 gap 达标时间、最终 U/L、节点数、LP 迭代数、通信量、空闲时间和可测能耗。

MILP 初轮至少三个种子；诊断集合可先少量运行定位错误，性能验收再使用三个至五个种子，对高波动实例增加重复。以实例或模型族为统计单位计算置信区间，不能把一个模型的数百相邻节点当作数百独立模型。[Gurobi 比较实验建议](https://support.gurobi.com/hc/en-us/articles/26992650628369-How-can-I-make-accurate-comparisons)

汇总必须包含已解数量、错误与失败数量、超时数量、逐实例结果、性能剖面和移位几何均值。若使用时间上限封顶的 SGM10，明确公式：

\[
\mathrm{SGM}_{10}=\exp\left(\frac1N\sum_i\log(t_i+10\mathrm{s})\right)-10\mathrm{s}.
\]

超时、数值失败、内存耗尽、崩溃、错误解及其他未达共同终点的运行，主 SGM 表统一以预先声明的时间上限作为失败计时；另列真实退出时间、失败原因和数量，不让快速失败降低均值。该代入只是描述性统计，不表示实例已解出。含正确性错误的配置不得通过性能门槛。共同解出子集只作为补充分析，不能替代完整集合。

固定时限的轨迹同时给可行目标和下界。综合 gap 面积可使用标准化时间内的积分，对缺失界/解设为预先声明的最差值；若使用 primal/dual integral，则固定参考目标来源与归一方式，并指出 best-known 不一定是已证明最优。

## 扩展效率的定义

同构资源下，同一算法、同一实例与终点定义：

\[
S(p)=T(1)/T(p),\qquad E(p)=S(p)/p.
\]

另与最佳可用单机算法比较，防止较弱单机实现制造漂亮扩展率。异构 CPU+GPU 组合不能简单按设备个数计算效率，应同时报告资源向量、成本和能耗。

在 1/2/4/8/16 个资源单元上测量，有资源和收益后再扩大。一个单元究竟是一块 GPU、一台机器还是固定核数，需要每张图明确。可拟合带饱和项的经验曲线 T(p)=T∞+a·p^(−α)，同时给残差、置信区间和拟合范围；样本不足时只画实测点，不外推幂律。

只有单资源与多资源均达到统一终点时才计算精确 S/E。单资源放不下、超时或质量未通过时，不能用封顶时间冒充 T(1)；容量提升单列，必要时给有严格前提的速度下界。目标族效率门槛使用预先固定族内的逐实例 E(8) 中位数，并展示完整分布和不可计算实例；不可计算实例不算过关，不在事后从族中删除。各实例跨种子先按预声明的中位达标时间计算效率。

固定实例叫强扩展；规模随资源增长叫弱扩展。MILP 变量数加倍并不意味着难度加倍，弱扩展必须控制结构与难度分布。仅增加独立实例数属于吞吐测试。

并行搜索的总工作量会改变，因此还需记录 W(p)/W(1)。W 使用 LP 迭代、处理非零元、CPU/GPU 时间与节点数共同描述，节点大小差异大时不能只数节点。偶发超线性或减速要结合搜索轨迹解释。

## 分阶段实验

| 编号 | 假设与方法 | 核心观测 | 决策 |
| --- | --- | --- | --- |
| E0 正确性基线 | 同一原模型跨后端求解；加入已知解、不可行、无界及病态案例 | 外部可行性、状态、下界、恢复一致性 | 验证失败先修语义，不进入性能发布 |
| E1 LP 路由 | simplex/IPM/PDLP 跨规模、结构、精度；比较冷启动与热启动 | 端到端时间、达标率、basis 成本、因子内存 | 确定 GPU 区间及 CPU 回退条件 |
| E2 自主 PDLP | 固定算法骨架，依次开启预条件、重启、融合、混合精度 | 迭代数与每步耗时分离；原模型残差 | 只保留可复现净收益组件 |
| E3 多 GPU LP | 同实例在 1/2/4/8 卡运行；包含低/高耦合与不均衡矩阵 | 分区、传输、迭代、恢复耗时；容量；切边率 | 确定最优卡数和扩展饱和原因 |
| E4 相关 LP | 固定真实节点/strong branching 序列，对比 CPU 热启动与 GPU 批处理 | 每批延迟、每个有效下界时间、慢实例、传输开销 | 必须进一步通过端到端 MILP 验证 |
| E5 单机 MILP 消融 | 每次只替换一个分支、割、启发式或 LP 路径 | 节点数、LP 总量、首解、gap 轨迹、已解数 | 区分搜索改进与单次计算加快 |
| E6 分布式搜索 | 同总资源比较独立 portfolio、共享 incumbent、协同子树 | E(p)、搜索膨胀、通信、尾部、成本 | 子树协作需胜过简单基线才增加复杂度 |
| E7 故障与终止 | 注入重复/乱序/延迟消息、worker/协调器崩溃、分区与重连 | 覆盖账本、有效界、恢复、错误终止 | 任何丢失区域或错误最优状态均阻断发布 |
| E8 学习预算 | 固定族隔离，分别增加数据、模型、训练与在线预算 | 保留集效果、推理成本、预算收益曲线 | 无可迁移净收益则保留基础策略 |
| E9 硬件评估 | 用真实轨迹与 Roofline、FPGA/仿真评估稳定热点 | 端到端能效/成本、带宽、精度和可编程性 | 达立项门槛后才考虑 ASIC |

E0/E1 为第一批工作；E2 与 E3/E4 中的一条构成近期主线。E5 先做成熟求解器的时间剖析。E6 至 E9 随依赖能力成熟推进，不要求当前无团队状态下同时开展。

E4 的固定序列回放用于隔离底层计算变化，E5 的真实搜索用于验证算法交互。E6 在相同机器总数下比较不同 CPU 线程/worker 划分，避免把线程超额分配当成并行收益。WAN 测试同时记录实际网络测量，模拟延迟只能作为补充。

热启动序列分别覆盖目标、RHS、变量界和增删行，统计完整序列耗时、尾部延迟、复用率、修复迭代和回退率。有 basis 输出要求时计入 crossover、基导出和传输。批处理回放加入动态割、局部行掩码、慢实例退出和矩阵版本切换，统计组批、重排、等待及界验证开销。

## 验收门槛与停止规则

以下是投入决策的初始建议，启动具体实验前冻结；之后改变必须说明原因并重新报告结果。

| 阶段 | 建议门槛 | 不通过时 |
| --- | --- | --- |
| 自主数值原型 | 在预先规定覆盖范围内全部通过外部质量检查；不要求首版立刻最快 | 缩小范围并修复，保留成熟后端 |
| GPU LP 投入扩大 | 预声明大型 LP 保留族 SGM10 端到端提升至少约 1.5 倍，达标数量不降；列出所有超过 2 倍减速实例 | 调整算法路由或缩小适用区间 |
| 批量 LP 进入 MILP | 有效下界/分支信息获取更快，端到端 MILP 保留族提升至少约 15%，已解数不降 | 留作独立实验，不设默认 |
| 多卡或多节点扩展 | 目标族达到 E(8)≥0.6 可继续研究；E(8)≥0.8 为接近线性研究目标；均报告分布与成本 | 限制资源数，定位通信、工作膨胀或串行段 |
| 通用策略默认启用 | 完整开发回归无新增错误，保留集净改善；家族性明显退化有可验证回退规则 | 保持可选，不用平均收益掩盖退化 |
| 分布式可靠性 | 全部覆盖/终止故障测试通过，无错误下界和错误最优状态 | 阻断发布，保留可重算模式 |
| ASIC 立项 | 稳定热点约占端到端 70%以上；优化 GPU 后仍有清晰瓶颈；完整系统预计约 3 倍能效或成本优势，并有需求与摊销依据 | 继续软件、GPU 或 FPGA 研究 |

扩展门槛针对预先定义的问题族和测量区间；不能在运行后只留下获益模型再宣布过关。若某实例不适合扩展，它仍留在通用评估表中，由路由器决定少用资源。

“通用达到 Gurobi”不由单一倍率决定。至少在固定公开集与独立保留集上，对同期适当配置比较已解数量、相同质量的 SGM、失败率、主要模型族退化和成本，连续多个版本保持。未覆盖的能力须单独列出，不能借测试集通过声称完整功能等价。

纯自研验收关闭外部求解器，单列自主路径覆盖率、数值困难比例及性能；混合系统另外报告回退次数与耗时。测试中未发现错误不表示所有可能输入均无错误，已知正确性缺陷必须关闭，并以达标数量约束过度拒绝求解。

ASIC 比较需覆盖预期投产时同期 GPU/CPU 的多个性能与成本情景，计入实际精度下的迭代变化、HBM、封装、传输、分区、互联和软件维护。算子能效改善不能直接当成系统能效改善。现有集群同样记录电力、维护和占用成本。

## 计算预算

首轮建议设软上限为 200 个 CPU 节点小时和 128 个 GPU 小时；CPU 节点按固定 16 核分配时约为 3200 核时。现有设备与配额清点后再确定实际上限。本计划不启动作业，也不代表用户批准新增付费资源。

诊断案例可先设每次 300 秒上限，验证完整后再扩到 1800 秒。正式 240 实例、3 个种子、4 个配置、每次 1800 秒，若全部超时，最多需要 1440 个配置运行小时；每个运行占 16 核时为 23040 核时。多节点测试应再乘每次运行占用的节点数，不能把墙钟小时当总资源小时。

每轮资源分配先做小样本判断；有明确改善趋势再扩大。保留原始日志和失败记录，重复运行限于新改动、波动调查和验收所需，避免用集群无限试参污染保留集。
